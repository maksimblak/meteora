## Что должно заработать

Python-сторона умеет говорить с TS executor: симулировать, отправлять и сверять команды по версионированным контрактам. Одобренная оператором команда исполняется worker'ом и после рестарта, выход не-SHADOW позиции идёт через gateway, а не только alert. Путь к реальной транзакции закрыт, пока не выполнены все проверки безопасности.

## Критерии приёмки

- [ ] адаптер `ExecutionGateway` поверх `POST /v1/simulations`, `POST /v1/commands` (с `Idempotency-Key`), `GET /v1/commands/{id}` с internal token; неизвестная версия контракта и неверная схема ответа отклоняются; Python-сторона проходит общий JSON corpus `contracts/execution/v1-corpus.json`
- [ ] таймаут или обрыв после отправки дают состояние UNKNOWN и сверку по статусу без повторной отправки; тот же `Idempotency-Key` не создаёт вторую транзакцию
- [ ] одобренная команда исполняется worker'ом через durable-разрешение плана (не in-memory resolver); после рестарта одобренная и не истёкшая команда исполняется ровно один раз, истёкшая — нет
- [ ] выход и уменьшение не-SHADOW позиции идут через свежую симуляцию и gateway; при недоступном gateway позиция остаётся под alert, без «тихой» потери
- [ ] kill switch перепроверяется непосредственно перед `gateway.submit` внутри `ExecutionService.execute`; при активном kill switch команда не уходит
- [ ] план, у которого после `SUBMITTING` пришёл `ExecutionBlocked`, остаётся EXECUTING до сверки и не освобождает ёмкость
- [ ] `build_entry_command` при mode ≠ SHADOW отказывает (fail-closed), пока в снимке нет active bin id и decimals токенов; смещения бинов никогда не уходят как абсолютные id
- [ ] ни один тест, команда разработки и запуск по умолчанию не отправляют транзакцию в сеть; интеграционный тест идёт против executor из compose без кошелька
- [ ] (после T10) воркер берёт политику из `load_pipeline_policy(os.environ)`: по умолчанию `guide-v1`, `RULESET_VERSION=shadow-hypothesis-v1` — прежняя версия, неизвестная версия — ошибка запуска
