**Требования:** R15, R17, G01, G04, G05, G06, G07, G08, G16, D06, D07, D08

**Модель:** сильная

## Что должно заработать

На настоящем API Meteora бот находит кандидатов, а не отклоняет все пулы. Короткие окна объёма честно считаются из кумулятивных счётчиков, новые пулы прогреваются из истории объёма, universe сужен до живых пулов, глубина меряется котировкой executor только для кандидатов, а якорь исполнения берётся из свежего состояния пула.

>
> «чтобы зарабатывать на всяких всплесках объёмов»
>
> «Все DLMM-пулы с жёсткими фильтрами»

## Критерии приёмки

- [ ] короткие окна 1–5 минут объёма и комиссий считаются из разницы `cumulative_metrics` соседних снимков: малые отрицательные разницы обнуляются, крупные отрицательные и интервалы вне допуска дают `UNKNOWN`; источник окна записан в snapshot и decision record; без look-ahead
- [ ] для кандидатов история прогревается из `/pools/{address}/volume/history?timeframe=5m`, с rate limit и кэшем; новый пул может получить решение без ожидания накопления своих снимков
- [ ] детекция всплеска, `VOLUME_DECAY` в `PositionMonitor` и короткий объём входа работают на этих окнах; выход Spot на сверхобъёме «при первом падении объёма» берёт отношение из плана позиции, а не общее из политики
- [ ] universe сужается фильтром на стороне API (по умолчанию объём за 24 ч > 0, настраивается); полный sweep без фильтра остаётся доступен явно
- [ ] полнота снимка определяется по полям живого API; на записанных фикстурах живого API часть пулов становится кандидатами, а не все `INCOMPLETE_MARKET_DATA`; есть тест на это
- [ ] глубина и price impact для кандидатов берутся из `POST /v1/quotes` executor (таск 13); нет котировки — флаг `DEPTH_UNAVAILABLE`: в SHADOW кандидат идёт дальше с консервативной моделью проскальзывания, в APPROVAL/LIVE вход закрыт
- [ ] `is_blacklisted` пула, `is_verified` и `freeze_authority_disabled` токенов из API входят в hard filters; органичность сравнивает с base fee сумму `fees + protocol_fees`
- [ ] `snapshot_anchor` читает `PoolSnapshot.active_bin_id` и decimals; перед входом не-SHADOW active bin перечитывается через `get_pool_states`, расхождение больше допуска отменяет вход; runtime передаёт адаптеру `pool_states` и фильтр universe
- [ ] `maximum_observation_gap` для доказательства ATH согласован с интервалом universe из конфигурации, а не задан отдельно
- [ ] (проба ревью T11) на живых снимках readiness выходит из `WARMING_UP`: baseline короткого окна копится из производных окон, `short_ratio` и `robust_z` считаются; есть тест на записанных фикстурах с историей снимков
- [ ] (проба ревью T11) в API нет числа транзакций и участников: проверка искусственного объёма опирается на доступные сигналы (turnover, органичность комиссий, самоподобие всплесков); нет сигналов участников — флаг `VOLUME_PARTICIPANTS_UNAVAILABLE`: SHADOW и APPROVAL идут дальше с флагом, видимым оператору, LIVE закрыт, пока сигнал не даст enhanced-провайдер
- [ ] (проба ревью T11) `PositionMonitor` не поднимает `MARKET_DATA_UNSAFE` на каждом живом снимке: полнота оценивается по полям живого API
- [ ] (находка T06) worker в конце каждых UTC-суток вызывает `PromotionEvidenceService.record_daily`: дни shadow-evidence накапливаются, и gate APPROVAL открывается по правилам §7.1, а не остаётся закрытым навсегда; тест на смену суток
- [ ] (находка T13) executor для котировок доступен в shadow-профиле compose без кошелька, а не только в профиле `live`; без executor котировок нет и действует `DEPTH_UNAVAILABLE`
- [ ] (находка T13) распределение суммы входа по токенам следует диапазону: Bid-Ask целиком ниже active bin — только quote-токен, без половины в base; диапазон через active bin требует оба токена, и если кошелёк не держит нужный токен (executor не делает swap), вход отклоняется с понятной причиной; `ACTIVE_BIN_TOLERANCE` — настройка политики, а не константа
