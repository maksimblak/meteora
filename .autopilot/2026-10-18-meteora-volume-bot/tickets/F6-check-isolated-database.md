# F6 — Ремонт после слепой приёмки: проверка не трогает рабочую базу

**Требования:** R22, R26i, R30i, G14
**Зависит от:** 20
**Зона:** `docker-compose.yml` (сервис `check` и комментарий у строки 18) · `tests/conftest.py` и общие фикстуры PostgreSQL в `tests/` (только выбор базы) · `README.md` (раздел про проверку) · `docs/runbook.md` (раздел про проверку)
**Волна:** 17
**Ревью:** нет
**Модель:** сильная

## Что должно заработать

Канонический check можно запустить рядом с работающим стеком (в том же проекте Compose, во время 7–14 дней SHADOW), и он не пишет ни строки в рабочую базу `meteora` и не спорит с работающим worker за аренды. Сейчас сервис `check` берёт `TEST_DATABASE_URL` = рабочая база `meteora`: часть тестов (например `tests/foundation/test_persistence.py`) пишет аудит и аренды в её общую схему, а при запущенном worker падают 3 теста (`tests/recovery/test_recovery_concurrency.py` — оба postgres-случая, `tests/worker/test_restart.py::test_all_jobs_run_under_leases_on_durable_storage[postgres]`). Тестовые записи в рабочей базе портят evidence для повышения режима.

## Найдено слепой приёмкой, дословно

> «Канонический набор проверок (`--profile test run check`) при запущенном стеке дал **3 failed** … С остановленными worker и api — всё зелёное. README не говорит, что стек перед проверкой нужно остановить.»

## Критерии приёмки

- [ ] `check` работает в отдельной базе (например `meteora_check`) того же postgres: создаёт её, если нет, мигрирует её (`alembic upgrade head` идёт в неё, а не в `meteora`) и отдаёт её тестам как `TEST_DATABASE_URL`; рабочая база `meteora` после прогона check не содержит ни одной записи от тестов
- [ ] доказательство: прогон check при поднятом в том же проекте стеке (`docker compose up -d` + `docker compose --profile test run --rm --build check`) — зелёный, 0 failed; число строк в таблицах аудита и аренд рабочей базы до и после check одинаковое (строки, которые за это время записал сам worker, отличаются по содержимому — сравни по признаку тестовых записей, способ опиши в CONCERNS)
- [ ] без поднятого стека check по-прежнему зелёный: не меньше 1284 passed, 13 skipped, executor 79
- [ ] README и runbook: одной-двумя строками — check можно запускать при работающем боте, он работает в своей базе; после проверки ничего чистить в рабочей базе не нужно
- [ ] комментарий `docker-compose.yml:18` про потолок priority fee в SHADOW приведён в соответствие с F4 (`shadow_priority_fee_lamports` — оценка, `PRIORITY_FEE_MAX_LAMPORTS` — потолок)
