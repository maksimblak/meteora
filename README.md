# Meteora Volume Bot

Локальное приложение для пулов **Meteora DLMM** на Solana: сканирует пулы, отбирает токены с устойчивым торговым объёмом так, как это делает автор гайда LexDollar (`guide-v1`), отсеивает подозрительные токены, накрутку и запрещённые темы, планирует одностороннюю LP-позицию (Bid-Ask с хаёв или Spot), ведёт её до выхода, продаёт монету, которую вернул выход, и считает результат после всех издержек в сравнении с простым удержанием (HODL). Работает в Docker, управляется через веб-панель на FastAPI.

## Чего бот не обещает

- **Доходность не гарантируется.** Это проверяемая гипотеза, а не способ заработка. Пороги взяты из гайда и двух видео автора и проверяются в SHADOW; их цифры доходности — утверждения автора, а не факты (см. [`research/`](research/)). Тейк-профит 5% / 3% — это порог выхода, а не ожидаемый результат сделки.
- **Это LP-позиции на активных монетах, а не накрутка объёма** и не обычная торговля: бот предоставляет ликвидность и зарабатывает только комиссии, а при падении токена позиция превращается в этот токен и может потерять почти всё. Продажа монеты после выхода фиксирует убыток, но не отменяет его.
- **Реальные деньги не тратятся по умолчанию.** Стартовый режим — `SHADOW` (симуляция без денег, кошелёк не нужен). Сделки с подтверждением и автоматический режим включаются только после допуска и вашего явного действия (см. «Режимы»).

## Что нужно

- Windows 10/11 с **Docker Desktop** (WSL 2) — запущенным; **PowerShell** (входит в Windows).
- Не меньше 15 ГБ свободного места на диске и интернет: Docker скачивает образы, бот читает публичный Meteora Data API (ключ не нужен). Из чего складывается (оценка для настроек по умолчанию: около 2 тыс. пулов в universe, шаг 5 минут, окно истории `HISTORY_RETENTION_HOURS` = 36 ч):
  - образы: около 2,5 ГБ (`api`/`worker`/`migrate` — один образ ~1,2 ГБ, `executor` ~0,5 ГБ, `postgres` ~0,6 ГБ); с профилем `gmgn` — ещё ~4 ГБ;
  - база: снимки пулов за окно истории — около 2–3 ГБ (≈ 3 КБ на снимок × пулы × снимков за окно; более частый шаг или `METEORA_UNIVERSE_FILTER=all` увеличивают объём пропорционально); решение по пулу пишется заново при смене исхода (статус, причины, флаги, режим, версия правил), но принятый кандидат записывается на каждом цикле; решения без плана живут в окне истории, а решение с планом хранится всегда — вместе до ~1 ГБ; журнал аудита не чистится и растёт на изменениях — порядка 50–100 МБ в сутки; плюс WAL PostgreSQL до 1 ГБ;
  - логи контейнеров: не больше 30 МБ на сервис (ротация 3 × 10 МБ).
  Итого за 7–14 дней SHADOW — около 8–10 ГБ. Объём тома базы: `docker system df -v | Select-String postgres-data`.
- Для тестов и приёмочного прогона дополнительно — [uv](https://docs.astral.sh/uv/) (Python ставится им сам). Для обычного запуска не нужен.

## Запуск до shadow-панели

Все команды — в PowerShell, из папки проекта (там, где лежит `docker-compose.yml`), например:

```powershell
cd "$env:USERPROFILE\Desktop\Meteora\MeteoraVolumeBot"
```

**1. Создайте `.env`** из шаблона. В шаблоне только имена переменных; значения вписываете вы.

```powershell
Copy-Item .env.example .env
```

**2. Впишите два значения** — токен оператора и секрет сессии. Сгенерировать случайную строку (64 символа):

```powershell
$b = New-Object byte[] 32; [System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($b); -join ($b | ForEach-Object { $_.ToString("x2") })
```

Запустите команду дважды и вставьте результаты в `.env` (`notepad .env`):

```
APP_OPERATOR_TOKEN=<первая строка>
APP_SESSION_SECRET=<вторая строка>
```

Остальное для SHADOW оставьте пустым. `DATABASE_URL` и `POSTGRES_*` заполнять не нужно — база настроена в `docker-compose.yml`. Токен оператора — ключ ко всем действиям в панели: не публикуйте его. Без токена стек тоже запустится, но панель будет только для чтения.

**3. Соберите и запустите стек:**

```powershell
docker compose up --build -d
docker compose ps
```

Первая сборка занимает несколько минут. Поднимаются `postgres`, `migrate` (применяет миграции и завершается с кодом 0), `api` (панель), `worker` (конвейер) и `executor-quotes` (котировки без кошелька). Логи: `docker compose logs -f worker` (выход — Ctrl+C). Можно запускать и без `-d` — тогда логи идут в это окно.

**4. Откройте панель:** http://127.0.0.1:8000

Сразу после старта universe `NOT_SYNCED`; первый sweep пулов идёт при старте worker, затем каждые 5 минут. Пока история не накопилась, пулы в статусе `WARMING_UP` (кандидатам историю подтягивает Data API за несколько минут, остальным пулам нужно около 40 минут снимков) — это нормально: бот не выдумывает сигналы на пустой истории. Отклонённые пулы видны с причинами в «Журнале решений».

**5. Войдите:** «Войти» → вставьте значение `APP_OPERATOR_TOKEN`. Вход нужен для действий (kill switch, смена режима, сбор evidence); просмотр открыт без входа.

**Остановить:** `docker compose down`. **Никогда не добавляйте `-v`** к этой команде на рабочем стеке: `-v` удаляет базу со всей историей, позициями и журналом.

### Рекомендуется: RPC для проверки токенов

Без Solana RPC бот работает, но не видит mint/freeze authority, держателей и возраст токена: такие решения помечаются `TOKEN_RISK_UNAVAILABLE` и **не засчитываются** в допуск к сделкам. Для полноценного SHADOW впишите в `.env`:

```
SOLANA_RPC_URL=<URL вашего RPC-провайдера>
EXECUTOR_INTERNAL_TOKEN=<ещё одна случайная строка>
```

Второе значение включает котировки глубины от `executor-quotes` (без него — флаг `DEPTH_UNAVAILABLE` и консервативная модель проскальзывания). Метрики GMGN — холдеры, total fees, объём и капитализацию токена (как в Trending GMGN), ATH токена, снайперов и статус девелопера — включает `GMGN_API_KEY=<ваш ключ GMGN OpenAPI>`: ключ создаётся на gmgn.ai/ai (для чтения токенов нужен только API key), тариф — `GMGN_API_PLAN` (по умолчанию `free`), проверка ключа — `docker compose exec worker uv run python -m src.gmgn.smoke --mint <адрес токена>`. После правки `.env`: `docker compose up -d`.

## Режимы

| Режим | Что происходит | Когда включается |
|---|---|---|
| `SHADOW` | симуляция без денег, кошелька нет | на свежей базе; после понижения, kill switch и дневного стопа (рестарт режим не меняет — он хранится в базе) |
| `APPROVAL` | реальные сделки, каждая — только после вашего подтверждения в карточке с ручным чеклистом | минимум 7 полных суток SHADOW подряд (рекомендовано 14), 20+ завершённых paper-позиций, положительный net expectancy, просадка ≤ 4%, покрытие данных ≥ 99%, нет открытых critical alerts; затем повторный ввод токена и подтверждение |
| `LIVE` | автоматические сделки | только из APPROVAL: 10+ подтверждённых циклов, сверенные receipts, готовые RPC и кошелёк, пройденный чеклист — в файле LIVE evidence; повторный ввод токена и подтверждение необратимости |

Переход `SHADOW → LIVE` напрямую запрещён; понижение и аварийный kill switch доступны всегда и действуют сразу. Переменная `TRADING_MODE` режим не включает. Лимиты риска во всех режимах: до 10% капитала в позиции, расчётный риск до 1%, не больше трёх позиций, дневной стоп 4%. На деле позицию ограничивает лимит риска, а не потолок 10%: расчётный убыток считается как размер × глубина диапазона, поэтому позиция выходит около **1,3–3,5% капитала** (Bid-Ask на 70–80% вниз — около 1,3%, Spot на 60% — около 1,7%, узкий диапазон в 70 бинов на малом bin step — до ~3,5%). Подробно, с настройкой executor для денежных режимов, — [`docs/runbook.md`](docs/runbook.md).

В `LIVE` ручной чеклист никто не проходит. Бот сам закрывает вход, если у девелопера есть доля токена (`DEVELOPER_HOLDS_TOKENS`) или она неизвестна, если нет свежих данных GMGN (`GMGN_UNAVAILABLE`, пока `GMGN_REQUIRED_FOR_LIVE` не выключен), если тема не проверена (нет имени и тикера), если нет числа сделок и участников, глубины по котировке или риска токена по RPC; тема из списка исключений, накрутка по total fees и флаг wash trading GMGN отклоняют кандидата в любом режиме. Twitter и хайп, гонку копий (PvP), кластеры Bubblemaps и «органичность» графика на глаз машина **не проверяет** — в LIVE этих проверок нет вовсе.

## Как бот отбирает и торгует (`guide-v1`)

Все числа — стартовые значения сборки и автора, настраиваются в `RULESET_OVERRIDES_FILE` ([`docs/configuration.md`](docs/configuration.md)) и проверяются в SHADOW.

- **Отбор как у автора.** Нужен устойчивый объём: средний объём токена в минуту за последний час **и** текущий объём в минуту (окно 5m) — не ниже 14 000 USD. Всплеск объёма больше не фильтр, а плюс к баллу (флаг `VOLUME_SPIKE`). Объём, капитализация и total fees — **по токену**: с ключом GMGN — объём токена GMGN, как в Trending; без ключа — сумма DLMM-пулов токена на Meteora (флаг `TOKEN_VOLUME_POOL_ONLY`). Из пулов одного токена оценивается основной — с наибольшими LP-комиссиями за час; на токен — одна позиция (`TOKEN_ALREADY_HELD`, в любом пуле и в любом порядке пары); глубоко проверяются только верхние 50 токенов цикла по часовому объёму (`CANDIDATE_RANK_BELOW_LIMIT`). Пулы, где монета стоит второй (SOL-МОНЕТА), пары из двух quote-токенов и пары без SOL/USDC/USDT отклоняются.
- **Фильтры автора.** Капа ≥ 500 тыс. USD, возраст ≥ 2 ч, top-10 < 30%, метрики GMGN; накрутка — total fees ниже 30 SOL × капа / 500 тыс. при обороте пула за час ≥ 10 × TVL или флаг wash trading GMGN (`ARTIFICIAL_VOLUME_SUSPECTED`); тема в имени или тикере (Илон, Маск, Трамп, MAGA, политики, стримы и т. п., в том числе склейки вроде `BABYTRUMP`) — `THEME_EXCLUDED`. Флаги без отказа: много снайперов (`SNIPERS_HIGH`), монета старше 60 дней (`TOKEN_REVIVED`).
- **Стратегия.** По умолчанию Bid-Ask с хаёв: вход, только если цена не ниже 90% от хая за последний час (`NOT_NEAR_LOCAL_HIGH`), ликвидность от цены вниз на 70–80%. Spot — односторонний, как у автора: только quote-токен, равномерно от цены вниз на 60%; только на пробитии ATH (ATH токена GMGN, без ключа — ATH пула с флагом `ATH_POOL_ONLY`, и капа ≥ 1 млн USD) или на сверхобъёме (≥ 100 000 USD в минуту). Обе позиции целиком ниже цены — для входа нужен только quote-токен, обмен перед входом не нужен (автопокупка для Spot снята). Slippage ликвидности — 30% ширины диапазона.
- **Выходы.** Тейк-профит по net P&L с комиссиями: 5% у Bid-Ask и Spot на ATH, 3% у Spot на сверхобъёме — **только в SHADOW**; сроки удержания: Bid-Ask до 24 ч, Spot на ATH до 3 ч, сверхобъём 30 мин; с ключом GMGN — выход, если девелопер продал (`DEV_SOLD`); плюс прежние выходы по диапазону, падению объёма и риску. Пулы открытых позиций перечитываются каждые 30 с.
- **Продажа монеты после выхода.** Выход из Bid-Ask на падающей цене возвращает монету; бот продаёт её в quote-токен в том же пуле (`SWAP_AFTER_EXIT`, включено по умолчанию): лимит price impact 3% на команду, минимальный выход −1%, при превышении — частями (до 4 делений пополам), до 5 попыток. Не продалось — монета остаётся в кошельке, critical alert, решение за вами ([`docs/runbook.md`](docs/runbook.md), §2.7).
- **Priority fee.** Executor ставит цену compute unit по 75-му перцентилю недавних priority fees сети, но не дороже 0,015 SOL на транзакцию (`PRIORITY_FEE_MAX_LAMPORTS`; поднимайте при нагрузке сети). SHADOW считает 0,001 SOL на каждую транзакцию входа, выхода и продажи — это стартовая оценка сборки, а не рыночные данные.

## Известные ограничения

Факты этой сборки — подробно в [`docs/runbook.md`](docs/runbook.md) и [`docs/configuration.md`](docs/configuration.md):

- **GMGN только по ключу.** Метрики GMGN (insiders, bundling, phishing, top-10, доля девелопера, total fees) бот берёт из официального GMGN OpenAPI, если задан `GMGN_API_KEY` (ключ создаётся на gmgn.ai, G20). Запасной сервис-браузер `gmgn` построен, но gmgn.ai через Cloudflare отдаёт headless-браузеру 403; обхода нет и не будет (никаких капч, stealth, подмены отпечатков). Без ключа бот работает с флагом `GMGN_UNAVAILABLE`, и автоматический LIVE закрыт, пока `GMGN_REQUIRED_FOR_LIVE` не выставлен в `false` осознанно.
- **Total fees токена** есть только у GMGN: порог условный, без значения (нет ключа или GMGN не ответил) — флаг `TOTAL_FEES_UNAVAILABLE` и строка в карточке подтверждения.
- **Без RPC** кандидаты в SHADOW не отклоняются, а идут с флагом `TOKEN_RISK_UNAVAILABLE` и не засчитываются для допуска в APPROVAL.
- **Meteora Data API не даёт окна 5m и глубины по бинам:** короткие окна считаются из разницы кумулятивных счётчиков, история кандидатов прогревается из `volume/history`, universe по умолчанию — пулы с объёмом за 24 ч (около 2 тыс. из ~139 тыс.; `METEORA_UNIVERSE_FILTER=all` — полный sweep), глубина — из котировки `executor-quotes` без кошелька.
- **Позиция — не шире 70 бинов (D10).** Официальный SDK открывает шире 70 бинов только цепочкой зависимых транзакций, а безопасной обработки оборванной цепочки в executor нет. Поэтому Bid-Ask на 70% вниз строится только в пулах с bin step около 176 и больше (авторские «мейнпулы bin step 200»); в остальных кандидат отклоняется `RANGE_TOO_NARROW`, и это заметно сужает выбор. Spot получает глубину, сколько дают 70 бинов, но не больше 60%.
- **Обмен токенов — только продажа монеты после выхода** (операция `SWAP` в том же DLMM-пуле, без агрегаторов вроде Jupiter). Обмена перед входом нет: Bid-Ask и Spot ставятся целиком ниже цены в quote-токене. Price impact входа проверяется по котировке SDK; выход им не блокируется; у продажи свой лимит. Часть продажи с неизвестным исходом держит позицию (и её слот из трёх) до сверки — ручного пути в панели нет (`EXIT_SALE_OUTCOME_UNKNOWN`, [`docs/runbook.md`](docs/runbook.md), §2.7).
- **Тейк-профит — только в SHADOW.** В APPROVAL и LIVE фактический net P&L позиции в этой сборке не измеряется, и тейк-профит не срабатывает (`take_profit=UNMEASURED` в событии и логе); выходы по срокам, диапазону, объёму и `DEV_SOLD` работают во всех режимах.
- **Priority fee в SHADOW — оценка.** 0,001 SOL на транзакцию (`shadow_priority_fee_lamports`) — стартовая оценка сборки; её сверяют с фактическими `priority_fee_lamports` в квитанциях APPROVAL. В пулах не к SOL её нечем пересчитать в quote-токен — она не учитывается (флаг `PRIORITY_FEE_UNPRICED`).
- **Ручной чеклист** обязателен в APPROVAL: для входа — Twitter/хайп, запас у девелопера, PvP, кластеры Bubblemaps, «график органичный» и «тема не Илон/Трамп/политика/стрим»; для выхода и продажи — первые четыре. В LIVE его никто не проходит (см. «Режимы»).
- **Данные GMGN кэшируются на 5 минут:** «текущий» объём токена может отставать до 5 минут; браузерный путь GMGN объём, ATH, снайперов и статус девелопера не даёт.
- **Ручная работа оператора:** частично прошедший выход переводит позицию в `OPERATOR_REQUIRED` с alert `POSITION_PARTIALLY_EXECUTED` — разбор вручную; critical alerts после разбора закрываются из панели (причина, повторный токен, запись в аудит), часть из них система закрывает сама после успешного действия; после ручного понижения до SHADOW выход APPROVAL-позиции панель одобряет только под дневным стопом или kill switch с `ORDERLY_EXIT` (вопрос открыт).
- **SHADOW-сутки** засчитываются, только если worker проработал их целиком: рестарт или сон компьютера стоят текущих суток.
- **Не реализовано:** ИИ-мониторинг соцсетей (отложен на вторую сборку), позиции шире 70 бинов, обмен через агрегаторы, уведомления (Telegram), отдельный стартовый live cap. Автопокупка для Spot снята по решению владельца: Spot односторонний.

## Проверки

- Канонический набор (миграции, линтер, типы, тесты Python и executor), всё в Docker:
  `docker compose --profile test run --rm --build check`
- Приёмочный прогон стека на записанных данных, без денег и внешней сети (около 10 минут, нужен uv):
  `powershell -ExecutionPolicy Bypass -File scripts\acceptance-smoke.ps1`
- Проверка папки поставки (всё на месте, нет `.env`, ключей, кэшей, `.git`):
  `powershell -ExecutionPolicy Bypass -File scripts\verify-delivery.ps1 -Path <папка>`
