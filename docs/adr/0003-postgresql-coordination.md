# 0003. Координация и состояние через PostgreSQL

## Контекст

API, worker и executor работают отдельными процессами и перезапускаются независимо; после рестарта нельзя терять позиции, повторять отправку транзакции или снимать дневной стоп (R30i, §5.4, §5.7).

## Решение

Единственный источник состояния — одна база PostgreSQL 16 из `docker-compose.yml` (volume `postgres-data`). В ней лежат снимки пулов, журнал решений и планов, позиции и учёт, режим и его переходы, risk days, alerts, approvals, состояние команд исполнения, transactional outbox и аудит; схема ведётся миграциями Alembic (`0001_foundation`, `0002_worker_state`). Задачи worker идут под leases в той же базе (`JobLeases`), денежные переходы — в транзакциях с optimistic version и advisory locks. API и worker открывают хранилища одной фабрикой `open_repositories` (D01). SQLite остаётся только адаптером для тестов и локальной отладки (`LOCAL_SQLITE_PATH`, запрещён при `APP_ENV=production`).

## Почему

- **SQLite-файл на процесс** (как строился учёт в T04) отвергнут (D01): два процесса с отдельными файлами расходятся в режиме, позициях и стопах, а общий SQLite-файл в Docker-томе не даёт надёжных блокировок между контейнерами.
- **Отдельный брокер (Redis, очередь) для координации** отвергнут: ещё один stateful-сервис со своим восстановлением, а гарантия «записано в аудит до отправки» всё равно требует транзакции в той же базе, где лежит состояние.
- **Состояние в памяти worker с периодическим сбросом** отвергнуто: рестарт между отправкой и записью оставлял бы транзакцию без следа и открывал повторную отправку.

## Последствия

- После рестарта worker сверяет незавершённые команды (`RecoveryService.reconcile(startup=True)`), а не отправляет их заново; режим, kill switch и дневной стоп переживают рестарт.
- Бэкап базы = бэкап всего состояния бота; процедура — в `docs/runbook.md`.
- Неприятное: база растёт. Очистка (`retention`) удаляет только опубликованные события outbox старше 7 дней; снимки universe и решения по каждому пулу на каждом цикле не чистятся, место на диске надо наблюдать.
- Неприятное: протоколы хранилищ синхронные, драйвер — asyncpg через мост-поток; из async-кода их вызывают через threadpool, это дороже прямого async-доступа.
- PostgreSQL в compose настроен с `POSTGRES_HOST_AUTH_METHOD: trust` и без опубликованного порта: доступ только из внутренней сети Docker.
