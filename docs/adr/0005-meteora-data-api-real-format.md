# 0005. Адаптер Meteora Data API под реальный формат ответа

## Контекст

План строил адаптер Meteora DLMM Data API по фикстурам T02. T10 показал: живой API отдаёт числа как float, `created_at` — epoch в миллисекундах, окна 5m нет, пагинация постраничная, и адаптер отклонял такой ответ целиком.

## Решение

Адаптер принимает тот формат, который реально отдаёт `dlmm.datapi.meteora.ag`. Числа на границе переводятся в `Decimal` через строковое представление, время — в UTC с часовым поясом. Universe обходится постранично с ограниченной конкурентностью; обход, в котором пулов меньше, чем заявил API, считается неуспешным и не заменяет последний целый снимок. Вместо окна 5m берётся наименьшее доступное окно, нормированное в минуту, с пометкой источника окна в снимке и решении. Тесты адаптера идут на записанных и очищенных ответах живого API.

## Почему

- **Строгий адаптер под фикстуры** отвергнут: формат задаёт Meteora, а не мы; с таким адаптером бот не видел ни одного пула (G04, R17), а написанные вручную фикстуры как раз и скрыли расхождение до T10.
- **Принимать float в домен как есть** отвергнуто: правило проекта — деньги только в `Decimal` или base units. `Decimal` из float тащит двоичный хвост в пороги и учёт; через строку значение совпадает с тем, что напечатал API.
- **Другой источник агрегатов (RPC, enhanced-провайдер)** отвергнут: RPC окон объёма не даёт, а SHADOW не должен зависеть от платного аккаунта (§3); Data API — единственный бесплатный источник агрегатов по всему universe.
- **Отклонять пул без окна 5m** отвергнуто: окна 5m нет ни у одного пула, это означало бы ноль кандидатов.

## Последствия

- Адаптер привязан к недокументированному поведению API: единицам, нумерации страниц, сдвигу страниц при изменении списка. Смена формата проявится как `DEGRADED` и неуспешные sync; ловит её ручной smoke против живого API, а не тесты на записях.
- Точность входных агрегатов не выше той, что дал API: float округлён ещё на его стороне, строковое преобразование лишь не добавляет своей ошибки.
- Неприятное: подстановка наименьшего окна (30m) вместо 5m на живых данных не сработала — всплеск и `VOLUME_DECAY` на получасовом окне не срабатывали. Короткие окна заменены разницей кумулятивных счётчиков (ADR 0008); остальная часть решения действует.
